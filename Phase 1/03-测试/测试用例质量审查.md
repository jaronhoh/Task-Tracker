# Phase 1 测试用例质量审查

## 1. 审查结论

- 审查对象：`Phase 1/02-PRD/PRD文档.md` 与 `Phase 1/03-测试/测试用例映射.md`。
- PRD 验收标准：187 条；已映射为 187 条基础用例，并有 12 条 D019 专项用例。
- 当前测试用例具备统一字段、编号和状态，但大多数基础用例的前置数据与步骤仍是通用模板；**不能直接视为全部已达到可重复执行的测试用例质量**。
- 本轮只做质量审查与建议，不擅自修改 PRD 已确认的业务规则；本文件不代表测试已执行。

## 2. 已确认的质量问题

### QG-01：前置条件没有绑定具体测试数据（高）

187 条基础用例普遍使用同一句通用前置条件，未明确具体 Task/Customer、初始状态、初始时间、输入值和预期数据库值。这会让不同测试人员执行出不同结果。

**建议：** 采用第 4 节的共用测试数据集；每条用例至少指定使用哪组数据及操作前的初始值。

### QG-02：部分验收标准把多个独立场景合并（高）

共识别 40 条可能需要拆分或在用例内建立子场景的验收标准。特别是跨多个 View、多个 Status、UI/API、多种失败条件、并发与原子性验证，应分别记录执行结果，避免一个用例部分通过却被整体标记为 Pass。

### QG-03：25 条验收标准含“或”条件（高/中）

“或”有时代表合理的替代交互，有时代表多个独立输入或实现选择。测试计划必须区分：
- 用户操作入口的替代路径：每条路径都要覆盖；
- 不同输入字段/状态：分别执行；
- PRD 允许两种不同实现结果：需产品确认唯一行为，或明确把两种都列为允许结果。

### QG-04：部分期望结果仍继承 PRD 的宽泛表述（中）

例如“清楚反馈”“明确错误”“符合规则”“当前时间”等，执行前需要把证据要求具体化：页面错误文本/错误类型、HTTP 状态码、时间允许的精度或容差、数据库最终值，以及是否无部分更新。若 PRD 没定义具体文案或精度，测试不得自行把建议值升级为产品要求，应记录为待产品/开发确认。

### QG-05：并发与原子性测试依赖环境能力（高）

Customer 名称/颜色并发竞争、Task ID 永不复用、同一 Task 写入顺序、事务回滚等测试，需要并发请求工具、数据库检查能力或故障注入能力。仅通过 UI 手动操作无法充分证明服务端约束与事务原子性。

**建议：** 将这些用例标记为 API/集成测试或数据库验证；注明所需工具和证据，不以 UI 表象替代验证。

## 4. 建议的共用测试数据集

以下是测试夹具建议，不是新增产品规则。实际执行时使用隔离环境，并记录实际创建的 ID 和时间。

| Fixture | 建议数据 | 主要用途 |
|---|---|---|
| CUST-A | Customer 名称 `QA Customer A`，由系统分配颜色 | 正常新增/编辑/搜索 |
| CUST-B | Customer 名称 `QA Customer B`，不同于 CUST-A | Customer 唯一性、改名、颜色唯一性 |
| CUST-16 | 16 个名称唯一的 Customer，全部占用调色板 | 颜色用尽、UI/API 禁止新增 |
| TASK-ACTIVE | Status = KIV，End = NULL，Created 为当前时间之前 | Active 正常行为、状态转换 |
| TASK-CLOSED | Status = Closed，End 有值且 End >= Created | Closed 编辑、恢复、End 校验 |
| TASK-DELETED | Status = Deleted，End 有值且 End >= Created | 逻辑删除、恢复、重复 DELETE |
| TASK-FUTURE | Created 晚于测试时钟当前时间 | D013 / D019 未来 Created 拒绝路径 |
| TASK-WEEK-START | Created 为星期一 00:00（Malaysia Time） | 当前周起点包含边界 |
| TASK-NEXT-WEEK | Created 为下周星期一 00:00（Malaysia Time） | 上周不包含、下周包含 |
| TASK-TEXT-BOUNDARY | Title 100 字符、Description 255 字符、Note 1000 字符 | 长度边界；另准备超长值 |
| TASK-CONCURRENT | 同一 Task 供多个并发写入请求使用 | D014 请求顺序与原子性 |

**测试数据注意事项：**
1. 时间边界测试需要固定时钟或记录准确的测试时刻；不使用模糊的“现在附近”。
2. “未来 Created”测试需确保 Created 晚于服务端时钟，而不是仅晚于客户端时钟。
3. Customer 颜色用尽测试应在独立数据集中执行，避免污染其他用例。
4. Task ID 永不复用测试需记录失败创建前分配的 ID，并验证后续创建不重复分配该 ID。
5. 对事务/原子性用例，应检查数据库最终状态或等效可信的持久化证据。

## 5. 建议优先级

| 优先级 | 范围 | 原因 |
|---|---|---|
| P0 | D019 Status/End 自动纠正、未来 Created 拒绝、无部分更新 | 直接影响核心数据一致性 |
| P0 | D014 同一 Task 写入顺序、Status/End 原子性 | 并发时可能产生错误最终状态 |
| P0 | Customer 名称/颜色唯一、16 色用尽、Customer 改名事务 | 防止数据冲突和部分更新 |
| P0 | Task ID 并发分配与永不复用 | ID 是永久标识 |
| P1 | Weekly Task / Current Week Status 周边界、Carry Over 与总数一致 | 影响每周汇报准确性 |
| P1 | PATCH 缺省/null/空字符串语义、API 错误结构 | 影响外部集成契约 |
| P1 | Auto Save 失败保留输入、请求按用户顺序发送 | 影响用户数据保存体验 |
| P2 | Dialog 尺寸、行高亮、状态颜色、Excel 文件名与列内容 | UI/导出体验和一致性 |

## 6. 执行前仍需明确的点

以下项目是测试可执行性风险，不代表 PRD 规则已被否定：

1. **AC-F01-01-03** 允许“阻止超限输入”或“拒绝提交并提示”。如果需要严格一致的 UI 自动化结果，需选定一种行为；若两种都可接受，测试需分别记录为可接受实现。
2. 对“明确错误/清楚反馈”，若需要自动化断言，应由开发提供稳定的错误代码或可测试的消息标识；PRD 未给出时，不自行编造错误文案。
3. 对“当前 Malaysia Time”的验证需明确系统可接受的时间精度/容差；PRD 未指定精度时，执行记录需注明实际时间及比较方式。
4. 对服务端串行、事务回滚和 ID 永不复用，需要可观测的服务端/数据库证据与可重复的并发测试方法。
5. 测试用例中每个“或”场景应确认是“替代入口”还是“不同输入分支”，再拆成子用例。

## 7. 审查结论

- **覆盖映射：** 187 条 PRD 验收标准均有对应基础用例。
- **测试设计质量：** 目前基础用例仍需具体化前置数据、输入步骤和可观测断言；不能只以覆盖编号完整来认定测试设计已成熟。
- **建议下一步：** 先完善 P0 的测试夹具与可观测断言，再对多条件 AC 拆分子用例，之后才进入实际执行。
